# 写作范式与示例

## 范式与适用边界

本技能将模块流程式 PRD 的结构整理为通用写作方法。使用时以当前任务提供的需求、模板和有效产品决定为准；不依赖任何内部文档访问权限。

本公开包不包含原始业务文档、人员资料、内部文档链接或产品原型附件。示例仅用于说明写作颗粒度，不是新项目的默认需求。

继承的稳定结构：

- 开头给出编制范围、有效口径和评审表。
- 主章节依次为变更记录、需求背景、涉及方、需求详细描述、实现状态与验收门槛、Q&A、附件清单与追溯。
- 全局先解释模块职责与页面归属；各模块再写用户任务、入口、状态、流程图、六列功能点表、完成定义。
- 功能点有稳定编号，原型关联到具体功能行，完成定义用可判断的结果描述。
- 当前行为、目标设计、待开发、设计差异与验证边界分开表达。

不继承的实例内容：固定九个模块、微信三 Tab、金融场景、手动或自动归档选择、确认次数、超时秒数、容量与字数限制、颜色与像素、接口地址、人员和历史完成结论。它们都必须由新任务的材料支持。

持续修订的 PRD 可能出现新正文与较早页面归属、实现状态或 Q&A 未同步的情况。局部规则改变时要校对所有引用位置，分清目标与现状，不复制旧结论。

## 六列功能表怎么写

| 列 | 写法 |
| --- | --- |
| 功能 | 模块编号和名称，同一模块多行可重复，富文档可合并单元格。 |
| 子功能 | 稳定编号＋动作或用户能力；一行能独立评审。 |
| 需求描述 | 有序短句，从触发写到反馈和结果，再写必要异常／边界；不用“优化体验”“支持管理”等空泛表达结束。 |
| 主要关联方 | 产品、设计、客户端、后端、硬件等实际相关方；关联方不自动等于承诺负责人。 |
| App 原型图 | 原型 ID＋状态名＋可用图片／链接；同一图可支持多行。无图、旧图、后台无页面都明确标识。 |
| 备注 | 当前实现、目标差异、依赖和待确认点；核心产品规则不能只藏在备注里。 |

## 纯软件适配判断

适用：软件的用户／调用方任务、操作或触发流程、业务规则、异常恢复和完成条件，均可由本范式描述。Web／SaaS 保留界面原型；无界面后台服务用业务交互关系与可观察处理结果替代 UI 要求。保留六列结构，不强求每项都有界面。

不充分：仅靠此模板不能代替 API 协议规范、技术架构、数据模型或测试执行报告。已有明确的非功能需求可以进入 PRD 完成定义，具体实现放技术方案。

评估时确认没有把“App 原型图”解释成必须有 App，没有引入硬件评审角色，没有把 AI 或特定金融规则当作通用要求。

## 中性示例：保存收货地址

以下仅演示颗粒度，不作为所有产品的默认保存策略。

**示例前提**：用户已说明需要“填写后保存；失败保留填写内容”，尚未提供原型、字段限制或现有实现。

**用户任务**：保存一条收货地址，供之后选择。

**入口**：地址管理页的“新增地址”。

**状态**：目标需求，当前实现未核验；必填字段与地区范围待确认。

| 功能 | 子功能 | 需求描述 | 主要关联方 | App 原型图 | 备注 |
| --- | --- | --- | --- | --- | --- |
| M01 地址管理 | M01-01 新增与保存 | 1. 点击“新增地址”进入填写页，字段与必填规则待确认。<br>2. 点击“保存”提交当前填写内容；建议提交中防止重复操作，待确认。<br>3. 保存成功后返回列表并显示新增地址。<br>4. 保存失败保留填写内容，显示失败原因并允许重试；不展示保存成功。 | 产品、客户端、后端 | 待补原型：填写、保存中、失败、保存后的列表 | 返回列表为建议交互，待确认；当前实现未核验。 |

**完成定义**：成功保存后列表可找到该地址；保存失败时原内容仍可编辑且不显示成功。返回位置和防重复提交规则确认后纳入正式验收；字段及地区范围未定前不声称功能已经具备完整验收条件。

流程可表示为“进入填写 → 用户保存 → 保存结果判断 → 成功呈现／失败保留并重试”；具体退出确认或默认地址逻辑不在此示例范围，不自行追加。

## 完成定义的边界

“支持保存”“交互友好”“接口正常”不足以判定完成。优先写成“在条件 A 下做 B，观察到 C；发生 D 时保留 E 并允许 F”。

完成定义描述用户和业务结果，不等于自动化测试脚本或验收报告。必要时映射到子功能 ID，不强迫每行写完整 Given/When/Then。已有验证记录注明范围、环境和时点；新改需求另列待验证。

## 交付自检

1. **范围**：覆盖了用户请求的全部模块或指定局部，没有为套模板增加新功能、页面、权限或平台。
2. **行为**：每个核心功能能回答入口、操作、反馈和结果；关键失败路径可恢复或明确结束。
3. **追溯**：模块和子功能 ID 唯一且引用有效；流程、原型、功能表和完成定义对应同一规则。
4. **一致性**：名称、默认值、限制、联动、删除／合并范围在摘要、正文、状态表、Q&A 一致。旧图的差异标在对应位置。
5. **证据**：建议、待确认、目标需求、原文记载与本次已核验事实可区分；未读取代码不声称已实现，未验收不声称上线。
6. **可用性**：表格没有一行塞进整套模块；没有未替换的模板提示；图片／链接真实存在；没有原型则明确缺口，不伪造素材。
7. **变更记录**：每次实际修改都有本轮记录，覆盖受影响章节／模块、主要变化与原因；历史保留且没有因重试重复追加。远端正文和记录均已回读；纯评审不伪造修订。
8. **交付状态**：请求范围的正文已完整生成；本地生成、远端写入、产品实现分别报告。
