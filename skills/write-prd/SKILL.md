# write-prd

以“用户要完成什么 → 从哪里进入 → 如何操作与反馈 → 得到什么结果 → 异常如何恢复”为主线，让产品、设计、研发和测试对同一版本形成可评审的共识。默认中文，跟随用户指定语言和产品术语。

## 适用范围与材料

- 支持从需求描述起草、从资料整理全产品、补写单模块，以及修订既有 PRD。单模块请求不扩写成全产品。
- 起草或重组时读取 [PRD 模板](assets/prd-template.md)；理解颗粒度、处理原型和校对一致性时读取 [写作范式与示例](references/writing-patterns.md)。
- 模板继承参考文档的结构，业务内容不继承。不要将参考中的微信平台、金融场景、模块数量、操作限制、人员、日期或实现结论带入新项目。
- 用户给出新的模板或明确结构时，以本次要求为准；不要强行覆盖。

## 标题与章节顺序

“变更记录”必须放在 PRD 正文最开始，紧接文档总标题；不在其前面放摘要、编制范围、资料基线、评审表、目录或其他正文内容。没有单独文档标题时，直接以“变更记录”开头。已有 PRD 的变更记录位于后方时，更新时将整个章节移到开头并保留历史记录。

除“变更记录”置首外，不固定其余标题的名称、编号、数量或排列顺序；按用户任务、材料和既有文档组织。配套模板中的后续章节及模块内部小节均为内容组织示例，不是强制目录或固定顺序。保留功能表、流程、完成定义等适用内容要求，不为套用标题顺序重排其余正文。

## 纯软件 PRD 的适用方式

本技能适用于 Web、SaaS、移动应用、小程序、桌面软件，以及后台服务／API 产品。核心结构围绕业务任务和可观察结果，不依赖硬件。

- 涉及方按实际选择产品、设计、前端／客户端、后端、测试、运维及数据／AI；纯软件默认不添加硬件／嵌软评审方，AI 也不是必选项。
- 有界面产品使用页面、弹层或组件原型；六列表头的“App 原型图”可按平台改为“界面／交互原型”。不因模板名称而增加 App 或移动端。
- 无界面的后台服务／API 产品，将“用户任务”理解为使用方或调用方的业务任务，“入口”写触发事件、调用或定时任务；原型列写“无界面，不适用”，必要时引用业务交互图，不要求绘制 UI。
- 按实际场景补足角色权限、数据可见范围、状态转换、失败恢复和外部服务依赖；有明确要求时记录可用性、响应时间等非功能完成条件及适用负载，不自造指标。
- 对纯接口协议、数据库结构或系统架构设计，本技能只能整理上层产品需求；详细实现由独立技术方案承接。

## 工作方式

### 1. 锁定本次范围

从用户材料中确认产品／平台、全产品或单模块、版本／本期范围、目标读者、输出位置，以及是在定义目标需求还是核对现状。

优先读取用户指定资料与已有 PRD。只有缺失信息会改变核心流程或范围时才集中询问；其余继续形成草稿，将未知项写为“待确认”，建议值标为“建议／待确认”。负责人、日期、性能阈值和业务上限不自行编造。既有材料已回答的问题不再追问。

用户只要求编写需求时，不必巡检代码、设计和生产环境；用户要求核对实现时才读取相关证据。拿不到材料时说明缺口，不把缺少证据写成未实现。

### 2. 分清目标、现状与证据

- **目标需求**：用户本轮明确要求及确认的有效产品决定。现有代码不能取消一个尚未实现的需求，也不能恢复已删除的需求。
- **当前行为**：由本次实际读取的代码、运行页面或服务记录支持；标明日期、环境和版本。来源仅为旧 PRD 时，写“原文记载／本次未核验”。
- **差异／待确认**：冲突资料分别说明适用范围和时点。不能判断时保留争议，不按“代码永远优先”或“最新文件永远优先”机械取舍。
- 区分待开发、待接入、代码已实现、已合并、已部署和已验收；设计同步状态另记。证据不够写“未核验”。新需求不能继承旧测试的通过结论。

### 3. 按用户任务拆模块

先定义模块承担与不承担的职责、入口及跨模块关系，再逐项展开。不要按数据库、接口或代码目录直接拆产品模块。

全产品保留全局流程与页面归属；单模块只写其上下游。沿用既有 M01 等模块 ID、M01-01 等子功能 ID 和原型 ID；合并／删除记录去向，不为编号连续而重排历史 ID。新产品可从 M01 开始。

每个模块覆盖以下适用内容，标题名称及排列顺序不固定：

1. **用户任务、入口、状态／边界**：一句任务描述，实际触发位置，必要前置条件，当前或目标状态。
2. **主流程图**：入口、关键操作、判断、成功结果及必要的失败／恢复分支。关系图与操作顺序图要区分；可跳过的步骤不能画成强制前置。
3. **功能点表**：保留“功能｜子功能｜需求描述｜主要关联方｜App 原型图｜备注”六列；纯软件可将第五列表头改为“界面／交互原型”，无界面功能标为不适用。
4. **完成定义**：写可观察、可判断的用户结果，并关联子功能；区分目标完成条件和当前验证结果。

### 4. 写到可以评审的颗粒度

每行描述一个可独立讨论的子功能，用有序句子说明：触发／前提、用户操作、系统反馈、成功结果、适用的失败与恢复、边界。简单只读功能不必机械补齐所有状态。

- 保留真实按钮名称、页面位置、默认值、排序／去重、返回与内容保留规则。数值或具体样式仅在材料有依据或作为明确建议时填写。
- 对提交类功能区分选择、草稿、提交、确认成功；对数据类功能区分未读取、空结果、无权限、不可用和读取失败，按场景选用。
- 描述功能联动和不应发生的副作用；不要默认“关注＝通知”“浏览＝授权”等未经确认的业务关系。
- 以产品行为表达规则。必要技术约束可以保留，但接口字段、数据库、部署步骤和详细测试脚本默认移入技术方案链接或附录；不要把 PRD 写成实现设计。
- 后台规则也可列为子功能，原型列写“后台规则，无独立页面”，不用虚构页面。

### 5. 绑定流程、原型与状态

原型放在对应功能行的“App 原型图”（或“界面／交互原型”）列，标注页面／状态名、ID、可用链接或图片；不能只在文末放一个无法对应的图包。该列沿用模板名称，实际可代表 Web、小程序或其他界面，不因此新增原生 App。

没有原型时写“待补原型：页面与状态”；只有文字说明时称为“原型说明”，不能声称已产出图片。既有截图、依据代码复绘、目标设计、历史旧图分别标明。旧图仍保留时，在对应单元格写出差异及有效规则。

流程可用 Mermaid；没有渲染工具时交付源码并如实说明未预览。仅在交付包含图形时检查其可读性、分支与正文一致性。创建 Figma、飞书画板或其他外部设计资产不属于默认写作步骤。

### 6. 每次更新必须同步变更记录

每次实际修订 PRD，都必须在同一份 PRD 的“变更记录”中追加本轮记录，正文与记录作为同一次交付完成。包括补写、删除、合并模块，修改规则、流程、原型、完成定义、实现状态，以及文案／排版调整；不能只在聊天回复中说明，也不能仅更新文档日期或版本号。

- 新建 PRD 在开头记录首次编制；已有文档缺少该章节时在开头补建并记录本次更新，不编造此前历史。只读取、评审或提出建议且未改动文档时，不虚构更新记录。
- 保留“修改时间｜修改内容｜修改人”三列。修改时间使用本次实际日期，同日多轮可加时间；修改内容注明受影响章节／模块 ID、主要前后变化和原因，适用时注明版本及实现／验收影响；未知修改人写“Codex 协助修订，负责人待确认”。
- 同一轮多个修改点可合并成一行，但须覆盖全部实质变化；后续独立更新追加新行，不覆盖、删除或重写旧记录。同一轮写入重试先检查已有记录，避免重复追加。
- 仅修改文档时明确“仅更新 PRD，未据此确认实现／上线”；不沿用已被新规则取代的验收结论。版本号按项目既有约定处理，不擅自升级。
- 即使只更新一个段落，也同时更新变更记录。远端写入后回读正文和本轮记录；任一部分未成功都不能报告完整更新成功，保留待补写内容和真实状态。

### 7. 收口并交付

按 [写作范式的自检项](references/writing-patterns.md#交付自检)核对正文、流程、功能表、完成定义、状态表和 Q&A。修订时将有效新规则合入原章节，同时更新受影响的入口、引用、摘要和 Q&A；变更记录保留历史，不让旧结论继续作为当前口径。

默认在聊天中交付；用户指定文件或外部文档时跟随指定位置。给出完整请求范围的 PRD，并简述主要待确认／待验收项，不以目录或计划代替正文。

飞书读写时使用当前环境可用的 lark-doc 技能，按其读取／创建／编辑流程执行；保存到既有文档时保留原 URL 和未受影响内容，写后回读核对。未要求发布时不自动创建或改写远端文档。只在工具成功并核验后报告已写入；能力不可用时保留完整本地或聊天草稿并说明状态。
